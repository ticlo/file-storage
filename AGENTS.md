# Repository Guidelines

## Project Structure & Module Organization

- `packages/file-server/src/index.ts` exposes the library surface `routeFileStorage`; keep reusable adapters and Hono route wiring in this package.
- `packages/file-server/dist/` is generated by the package build; never edit compiled code or declaration files by hand.
- `app/` hosts the local Hono harness (`app/index.ts`) and shared helpers (`app/session.ts`, etc.) used while developing routes.
- `www/` serves static assets through the dev server; treat it as public output only.
- `files/` mirrors sample storage trees (grouped by `proj/` and `usr/`) for local fixtures; do not commit secrets.

## Build, Test, and Development Commands

- `pnpm install` - install dependencies with the pinned pnpm 10 toolchain.
- `pnpm dev` - run the Hono dev server on http://localhost:8047.
- `pnpm run build` - compile `@ticlo/file-server` to `packages/file-server/dist` via its package build.
- `pnpm run lint` - run ESLint across `packages/file-server/src` and `app`.
- `pnpm exec prettier --check "packages/file-server/src/**/*.ts" "app/**/*.ts"` - verify formatting matches Prettier defaults.

## Coding Style & Naming Conventions

- Use TypeScript, ES modules, and two-space indentation.
- Prefer `camelCase` for variables/functions, `PascalCase` for types, and `kebab-case` for filenames.
- Keep Hono route handlers pure; push side effects into dedicated helpers.
- Honor the relaxed ESLint config (unused variables disabled); still remove dead code unless purposely stubbed.
- Format with Prettier before committing; avoid manual alignment that Prettier will rewrite.

## Testing Guidelines

- No test runner is wired up yet; add coverage alongside features using `*.spec.ts`/`*.test.ts` patterns supported by ESLint.
- Favor Hono's `app.request()` or the shared test server for HTTP-level tests and isolate filesystem fixtures under `files/fixtures`.
- Until automated tests exist, run `pnpm run build` and exercise endpoints via `pnpm dev` (which already watches the package compiler) before merging.

## Commit & Pull Request Guidelines

- Repository history is minimal; use imperative, present-tense subjects (`Add route guard`) and keep scope focused.
- Reference issues or TODOs in the body; include reproduction steps or follow-up tasks when behavior changes.
- PRs should summarize the change, list manual test evidence (commands run, endpoints hit), and attach screenshots for UI-affecting assets in `www/`.
- Request at least one review for changes touching `src/` or shared auth helpers.
- Update documentation (`AGENTS.md`, README) whenever API contracts or directory layout shifts.
